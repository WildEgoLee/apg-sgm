# SGM Workspace Allocation Audit

**Scope:** source-only audit of current SGM allocation and lifetime behavior. No runtime heap instrumentation or algorithm changes were made. The default configuration is 4-path SGM; the packed backend is the primary path considered below.

Let `N = width * height`, `S = sum(pixel search widths)`, `D = dense disparity count`, and `T = active OpenMP workers`.

| Allocation site | Requested size / capacity | Frequency and ownership | Lifetime and reuse |
| --- | --- | --- | --- |
| Packed cardinal `PathState::prev.vals` and `cur.vals` in `aggregate_path_packed` | Each grows to the largest per-pixel search width `D_p` seen on that scanline; capacity is at least that high-water mark, with allocator growth slack implementation-dependent. | Path4 runs 2 horizontal passes over `H` lines and 2 vertical passes over `W` lines. Each line body constructs its own pair, so normally there are two first-growth allocations per non-empty line: up to `4 * (H + W)` initial vector allocations, plus any capacity-growth reallocations. `cur.vals.resize(D_p)` and `prev = cur` run per pixel (4N of each for Path4). Objects belong to the OpenMP loop iteration, not to the worker. | Destroyed at the end of each scanline iteration; capacities are not reused by the next line, opposite direction, or frame. `prev = cur` copies the path state each pixel even when it does not allocate. |
| Packed diagonal `prev.vals` and `cur.vals` | Each grows to the largest `D_p` encountered in that diagonal direction. | Path8 adds four serial diagonal passes; one pair is shared across all rays within a direction. Up to eight initial vector allocations per frame, plus growth reallocations. | Reused across rays in one direction, then destroyed when that direction returns. No reuse across directions or frames. |
| `seen` in packed and dense diagonal passes | `N` bytes (`std::vector<uint8_t>`). | One allocation and zero initialization per diagonal direction: four times per Path8 frame. The diagonal pass is serial. | Lives for one diagonal-direction call and is recreated for the next direction/frame. Not present in Path4. |
| Dense cardinal `prev` and `cur` | Each requests `D` integers (`4D` bytes). | Two vectors per scanline iteration over the same `2H + 2W` cardinal lines: `4 * (H + W)` vector allocations per Path4 frame. They are owned by individual loop iterations under `schedule(dynamic, 4)`. | Destroyed after each line. `prev = cur` still copies D integers at each pixel; no repeated allocation while the vectors exist. |
| Dense diagonal `prev` and `cur` | Each requests `D` integers. | Two vectors once in each of four serial diagonal calls. | Reused across rays in that call; destroyed at its return. |
| Packed `cost32` accumulator | `S` `uint32_t` values (`4S` bytes); its shared layout has `N+1` `uint32_t` offsets and `N` `int16_t` minima. | One packed layout build per frame. Pipeline allocates/zeros `cost32` before `optimize_packed`; because both volumes receive the same layout pointer, `optimize_packed` then performs another full `fill(0)`. Thus the accumulator gets two full zero passes before path accumulation in this call path. SGM path passes update it sequentially. | Lives through all path passes and WTA, and remains in caller-owned `PipelineBuffers` after `compute` returns. The next packed call explicitly invokes `release()` before allocating again. Direct calls to `optimize_packed` can reuse a matching accumulator, but the pipeline currently prevents that reuse and redundantly clears it. |
| Dense `cost32` accumulator | `N * D` `uint32_t` values (`4ND` bytes). | One zero-initializing `allocate` in `optimize`; path passes accumulate sequentially. | Remains in `PipelineBuffers` after return, but the next dense call invokes `release()` before rebuilding. `release()` uses `clear()` plus `shrink_to_fit()`; actual capacity release is implementation-dependent. |

## Reuse implications

- The cardinal scratch objects are line-owned, not thread-owned. A worker can process many lines, but each line reconstructs and discards its vectors. Reusing two buffers in the worker scope of a persistent `omp parallel` region would eliminate most per-line first-growth allocations while keeping the path recurrence and path ordering unchanged.
- `StereoMatcher::compute` constructs `SgmOptimizer` locally on each call, so making scratch an ordinary optimizer member would not persist it across frames. Cross-frame reuse needs an owner whose lifetime spans calls (or an explicitly thread-local workspace) and a defined policy for concurrent calls and changing thread counts.
- Buffer reuse alone will not remove the per-pixel `prev = cur` state copy. Treat that copy as a separate data-movement cost; changing it is outside this allocation audit.
- `PipelineStats::estimated_peak_bytes` counts cost volumes, packed layout, and Cross workspace, but not recurrence vectors or diagonal `seen` storage.

**Next audit-backed candidate:** make cardinal `prev/curr` storage worker-owned for one path pass, then remove the redundant packed `cost32` setup/clear and explicit release only after separate correctness and performance review. No implementation change is included here.
